# HTTP Header 3파트 연재 계획

확정일: 2026-10-24. 사용자가 정한 범위를 기준으로 한다. 세 편을 한 번에 완성하지 않고 현재 편부터 편집한다.

| 파트 | 범위 | 글의 흐름 |
| --- | --- | --- |
| 1 | 필요성, 표현 선택·해석, 압축 | 왜 헤더를 알아야 할까 → 보내는 형식과 받고 싶은 형식 → 실제 압축과 복원 |
| 2 | 캐시·재검증, 인증, 상태 유지 | 저장한 응답을 다시 써도 될까 → 자격 증명 제출과 검증 → 쿠키로 요청 사이의 상태 연결 |
| 3 | 다른 출처의 응답 읽기, 브라우저 보안 정책, 이동·다운로드·부분 조회 | 실제 사례를 재현하고 요청·응답과 브라우저 동작으로 원인·해결 확인 |

## 1편 — HTTP 헤더, 무엇을 주고 어떻게 받을까?

[통합 초안](BLOG-01-header-roles.md)의 도입과 간단한 역할 지도를 유지한다. 상세 설명은 [표현 선택·해석](SECTION-01-representation.md)과 압축까지만 담는다. 캐시·인증·쿠키·브라우저 정책의 설명은 후속 편으로 넘긴다. 기존 [압축 상세 자료](SECTION-02-compression.md)는 기술 참고 자료로 보존한다.

## 2편 — 응답을 다시 쓰고 사용자를 확인하는 방법

- Cache-Control은 정책, ETag·Last-Modified는 검증 기준, Vary는 응답 선택 조건으로 연결한다.
- ‘ETag를 써도 결국 DB 조회는 필요한가?’라는 사용자의 질문을 중심으로 비용을 설명한다.
- Authorization·WWW-Authenticate와 401·403을 요청 흐름 안에서 설명한다.
- Set-Cookie·Cookie로 상태가 이어지는 과정을 설명하고 인증과 상태 유지의 관계를 구분한다.
- 아직 본문 완성·실습 검증 전이다.

## 3편 — 브라우저에서 마주치는 문제로 읽는 HTTP 헤더

다음은 사례 후보이며 사용자가 실제 경험한 사건이라고 쓰지 않는다. 재현 전에는 시나리오, 실행 후에는 재현 조건과 결과를 명시한다.

- curl에서는 되는데 브라우저에서 응답을 읽지 못한다: CORS와 preflight.
- 외부 스크립트가 실행되지 않는다: CSP와 Console 메시지.
- URL을 옮긴 뒤 요청 메서드가 달라진다: Location과 리다이렉트 상태 코드.
- 파일을 다운로드시키고 싶다: Content-Disposition과 파일명.
- 큰 파일을 이어받고 싶다: Range·Content-Range와 206·416.

사례마다 증상 → 관찰 → 원인 → 변경 → 재확인 순서로 쓴다. 전체 옵션 목록은 공식 문서로 연결한다. 아직 사례 구현·검증 전이다.
